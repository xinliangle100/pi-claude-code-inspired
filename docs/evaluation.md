# 后续验证（不是现成效果结论）

先锁定 source-faithful 版本，再对比，不把个人增强偷偷放入基线。

选择同一组真实代码库功能任务：固定提交、需求、模型、thinking level、工具权限与预算。对照原生 Pi 与本包，各用独立工作树。记录：
- 最终是否沿用合理的既有边界、是否无故增加平行体系。
- 方案审批前发现的重要约束，以及实现后才发现的返工原因。
- 测试/功能结果、人工结构评审、修改范围、总耗时和实际token/费用。
- 七阶段、等待用户、并行人数、review阈值是否真的遵守，不能只统计工具出现次数。
- 未实现工具、父上下文未自动传递、模型映射造成的能力缺口。

需要用户回答的任务按相同信息与准则回答。多次运行，保留失败例，不用单次成功宣称更优。若以后加入 architecture gate / decision ledger 等增强，另开版本或开关，并在来源表明确标注“本项目增强”，不要将其追认成上游原始能力。
